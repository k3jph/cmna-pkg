# CMNA R Package Architecture

This document defines the technical architecture for CMNA 2.0 in `cmna-pkg`. It describes the package as it should evolve on `develop`, including module boundaries, public contracts, numerical behavior, testing, documentation, and release controls. The companion [roadmap](ROADMAP.md) explains why the modernization is underway and the order in which algorithm families will be addressed.

## 1. Architectural goals

The architecture serves five goals.

1. **Teach the algorithm.** Implementations should remain readable enough to accompany a numerical-analysis text.
2. **Behave like a real package.** Public functions require stable contracts, validation, useful failures, documentation, tests, and automated checks.
3. **Make numerical failure explicit.** A routine must not silently return an invalid, non-finite, or unconverged result as a successful answer.
4. **Modernize incrementally.** Existing algorithm families can be brought to the new standard without requiring a flag-day rewrite of the entire package.
5. **Support a companion implementation.** Semantics should be comparable with `cmna-el` while retaining idiomatic R interfaces and package structure.

These goals deliberately favor clarity and correctness over abstraction density or peak performance.

## 2. System context

`cmna-pkg` has three related audiences:

- readers of *Computational Methods for Numerical Analysis with R*;
- R users who want inspectable reference implementations; and
- maintainers extending or correcting the package for CMNA 2.0.

The package sits between mathematical exposition and production numerical libraries. It should be more robust than a loose collection of textbook snippets, but more transparent than an optimized library whose implementation details are intentionally hidden.

The package should rely primarily on base R. Additional runtime dependencies require a clear instructional or architectural justification. Development tools such as `testthat`, `roxygen2`, package checking, coverage, linting, and pkgdown remain development concerns rather than reasons to complicate the runtime dependency graph.

## 3. Repository structure

The target repository structure follows standard R-package conventions.

```text
cmna-pkg/
├── DESCRIPTION
├── NAMESPACE                 # generated by roxygen2
├── README.md
├── ROADMAP.md
├── ARCHITECTURE.md
├── NEWS.md                   # release-facing change history
├── R/                        # implementation and roxygen source
├── man/                      # generated Rd documentation
├── tests/
│   ├── testthat.R
│   └── testthat/             # unit, invariant, and regression tests
├── vignettes/                # longer instructional material when needed
├── _pkgdown.yml              # website organization when present
└── .github/workflows/        # checks, lint, coverage, and documentation
```

Generated files must have a single source of truth:

- `NAMESPACE` and `man/*.Rd` are generated from roxygen comments in `R/`;
- pkgdown output is generated from package metadata and documentation;
- generated files should not be hand-edited as a substitute for correcting their sources.

## 4. Package layers

The codebase is organized into four conceptual layers.

### 4.1 Public algorithm layer

This layer contains the functions users call: root finders, decompositions, interpolators, quadrature routines, optimizers, and differential-equation solvers.

A public function is responsible for:

- presenting the documented API;
- validating user-facing arguments;
- normalizing harmless variations such as reversed interval endpoints when the method permits it;
- calling any internal helpers;
- enforcing the documented convergence or completion rule; and
- returning the documented result or raising a useful condition.

Public functions should not depend on unrelated algorithm families merely to share a few lines of code.

### 4.2 Domain implementation layer

Closely related public functions may share private implementation routines within the same numerical domain. Examples include:

- bracket validation shared by bracketing root finders;
- matrix-shape checks shared by linear-algebra methods;
- sample-point normalization shared by interpolators;
- objective evaluation shared by optimization variants; and
- time-grid validation shared by ODE solvers.

A domain helper should exist because it expresses a stable concept, not merely because two functions currently contain similar syntax.

### 4.3 Package utility layer

Small internal helpers may provide genuinely package-wide behavior such as:

- scalar numeric validation;
- finite-value checks;
- positive tolerance and iteration-limit validation;
- standardized convergence-failure messages; and
- approximate numeric comparison used by internal diagnostics.

Internal helpers should use an unmistakably private naming convention, such as a leading dot and a `cmna` prefix, for example `.cmna_validate_tolerance()`. The exact helper set should emerge from repeated requirements; CMNA should not acquire a large framework before the algorithms demonstrate a need for it.

### 4.4 Tooling and generated layer

Tests, roxygen output, pkgdown, lint configuration, coverage, and GitHub Actions support the package but are not part of its numerical runtime architecture.

## 5. Dependency direction

Dependencies should flow downward:

```text
public algorithm
    ├── domain-private helper
    └── package-private utility
             └── base R
```

The following rules apply:

- package-private utilities must not call public numerical algorithms;
- low-level utilities must not depend on high-level domains;
- algorithm families should not form cycles;
- examples and tests may compose public algorithms, but production code should do so only when the composition is mathematically intrinsic and documented; and
- optional presentation or website tooling must not become a runtime prerequisite.

## 6. Domain organization

Files in `R/` should be organized by coherent numerical domain rather than by arbitrary file size. The exact filenames may evolve, but the conceptual boundaries are:

- fundamentals and floating-point examples;
- linear algebra;
- interpolation and extrapolation;
- numerical differentiation;
- numerical integration;
- root finding;
- optimization;
- ordinary differential equations;
- partial differential equations; and
- instructional applications and sample functions.

A file may contain one substantial algorithm or several tightly related small algorithms. It should not become a miscellaneous dumping ground merely to reduce the number of files.

Each modernized family should begin with a short package-maintainer view of its common contract: accepted shapes, tolerance meaning, iteration semantics, and failure conditions.

## 7. Public API contracts

### 7.1 Naming

Existing public names are part of the package's historical interface and should not be renamed casually. When a name is unclear or inconsistent, the preferred sequence is:

1. document the problem;
2. decide whether correction is necessary for 2.0;
3. add a new name or signature where appropriate;
4. provide a documented deprecation path when feasible; and
5. record the change in `NEWS.md` and release notes.

New arguments should use consistent vocabulary across families. Preferred concepts include:

- `tol` or another single package-wide tolerance name;
- `maxiter` or another single package-wide iteration-limit name;
- `f` for a function only where this remains clear in documentation;
- explicit initial estimates such as `x0` and `x1`; and
- explicit interval endpoints rather than overloaded vectors when the method naturally requires two bounds.

The final vocabulary should be chosen once at package level and applied consistently.

### 7.2 Validation

Public functions validate assumptions that can be checked cheaply and unambiguously. Depending on the method, this includes:

- required arguments are present;
- function arguments are functions;
- scalars are numeric, length one, non-missing, and finite;
- counts are finite positive whole numbers;
- tolerances are finite and strictly positive;
- matrices and vectors have permitted dimensions;
- sample points have compatible lengths and valid ordering;
- intervals or brackets satisfy method-specific requirements; and
- derivatives, objective values, and iterative updates remain finite.

Validation should occur before expensive work and again during iteration when user-supplied functions can produce invalid values later.

### 7.3 Return values

The simplest mathematically natural return should remain the default.

- A scalar root finder should normally return a scalar root estimate.
- An interpolation function may return a scalar, vector, or callable result as documented by that method.
- A decomposition may return a named list when multiple matrices are intrinsic to the result.
- A trajectory solver should return a consistent tabular or structured representation rather than changing shape based on a special case.

Diagnostic-rich return objects should be introduced only through a deliberate package-wide decision. Until then, failure diagnostics belong in conditions and documentation rather than ad hoc attributes that differ by function.

### 7.4 Errors and warnings

Use an error when the function cannot satisfy its contract or produce a valid result. Examples include:

- an invalid bracket;
- a singular or dimensionally invalid matrix;
- a zero derivative or denominator that prevents continuation;
- a non-finite function evaluation;
- floating-point stagnation before convergence; and
- exhausted iteration limits.

Warnings are appropriate only when a valid result is returned but the caller should know about a degraded or surprising condition. A warning must not be used to disguise non-convergence.

Error messages should identify:

1. the failed condition;
2. the relevant argument or numerical state; and
3. the action needed when it is reasonably clear.

Tests should generally assert the condition class or a stable message fragment rather than an entire sentence whose punctuation may change.

## 8. Numerical behavior

### 8.1 Purity and state

Numerical functions should be deterministic for fixed inputs unless randomness is part of the documented method. They should not modify global options, the caller's objects, the random-number state unexpectedly, or hidden package state.

Randomized methods must document their relationship to R's RNG and must be testable under an explicitly set seed.

### 8.2 Finite arithmetic

Iterative methods must treat `NA`, `NaN`, `Inf`, and `-Inf` as explicit numerical events. They should not allow a non-finite intermediate value to circulate until a later comparison fails mysteriously.

### 8.3 Convergence

Every iterative algorithm requires:

- a documented convergence measure;
- a positive tolerance;
- a finite iteration budget;
- an immediate-success rule when the initial state already satisfies the problem;
- detection of method-specific breakdown; and
- an error on iteration exhaustion unless the API explicitly returns a status object.

A small step is not automatically convergence. When appropriate, convergence should consider the residual, interval width, objective change, or other mathematically relevant quantity.

### 8.4 Floating-point stagnation

Algorithms should detect when the next representable state is indistinguishable from the current state before the documented criterion is met. Examples include:

- a midpoint equal to an interval endpoint;
- an update equal to the current estimate;
- a denominator too small to produce a meaningful step; and
- repeated objective or residual values caused by finite precision.

The response should be method-specific and explicit: accept only if the convergence contract is satisfied; otherwise raise an informative error.

### 8.5 Readability versus performance

CMNA implementations should avoid gratuitous inefficiency, but their first optimization target is conceptual clarity. Vectorization, caching, or helper extraction is welcome when it preserves the visible structure of the method. Replacing an educational algorithm with a call to a production solver defeats the package's purpose unless the call is being used only for validation or comparison in tests and examples.

## 9. Documentation architecture

Roxygen comments beside each public function are the authoritative API documentation. They should include:

- a concise statement of the method;
- parameter definitions and constraints;
- the mathematical meaning and shape of the returned value;
- method assumptions and important breakdown cases;
- executable examples using valid data; and
- family tags or cross-references where useful.

Longer conceptual explanations belong in vignettes, the book, or pkgdown articles. The help page should remain sufficient to use the function correctly without consulting the source.

Examples used in the book and package should share canonical cases when possible, reducing the risk that prose and software drift apart.

## 10. Testing architecture

The test suite uses `testthat` and should contain several complementary forms of evidence.

### 10.1 Contract tests

Verify validation, argument normalization, documented defaults, return types, and expected conditions.

### 10.2 Canonical numerical tests

Use problems with known analytic or high-confidence reference solutions. Assertions should use tolerances justified by the algorithm and test case rather than a universal decimal count.

### 10.3 Invariant tests

Where possible, test mathematical properties rather than individual outputs alone. Examples include:

- root residuals are small;
- a decomposition reconstructs the original matrix;
- an inverse approximately yields the identity;
- interpolants reproduce supplied nodes;
- quadrature integrates suitable low-degree polynomials exactly or to the expected tolerance;
- ODE error decreases at the expected order under step refinement; and
- optimization results improve the objective relative to the initial state.

### 10.4 Failure-mode tests

Each documented breakdown path should have a test: invalid shapes, non-finite evaluations, zero denominators, singularity, stagnation, and iteration exhaustion.

### 10.5 Regression tests

Every corrected bug should receive a test that would fail under the prior behavior.

### 10.6 Cross-implementation cases

When the same method exists in `cmna-el`, a small set of canonical inputs may be represented in both test suites. These are semantic parity tests, not byte-for-byte result requirements.

Tests should not depend on network access, wall-clock timing, platform-specific display behavior, or mutable external data.

## 11. Quality gates

A change is eligible for merge into `develop` when applicable checks pass:

- package tests;
- R CMD check on the supported matrix;
- lint;
- coverage reporting;
- roxygen output is current;
- examples execute successfully; and
- pkgdown can build when documentation structure is affected.

A green check is necessary but not sufficient. Review must also confirm that the implementation matches the mathematical method and the documented contract.

## 12. Compatibility and versioning

CMNA 2.0 may correct interfaces whose historical behavior is unsafe or ambiguous, but changes should be deliberate.

- Bug fixes that make documented behavior work do not require preservation of the bug.
- Signature changes require migration notes.
- Removed or renamed public functions should receive a deprecation period when practical.
- Return-shape changes require especially careful review because they can silently break downstream code.
- The `main` branch remains the stable release line until the complete 2.0 release is approved.

Version 2.0.0 should represent a coherent package-level contract, not merely the passage of time.

## 13. Relationship to `cmna-el`

The two repositories share a mathematical architecture but not a source architecture.

Parity means that both implementations agree on:

- what problem the method solves;
- required mathematical preconditions;
- convergence and breakdown concepts;
- canonical examples; and
- whether a difficult state is success, failure, or unsupported input.

R-specific architecture remains authoritative here: vector and matrix conventions, R conditions, roxygen, package exports, and testthat should not be distorted to imitate Emacs Lisp.

## 14. Architectural decision process

A change should be recorded in this document or a future `docs/decisions/` record when it affects more than one algorithm family or creates a long-lived compatibility constraint. Examples include:

- the package-wide tolerance and iteration argument names;
- adoption of structured diagnostic return objects;
- supported R-version policy;
- matrix and trajectory return conventions;
- error-class strategy;
- dependency additions; and
- shared cross-language test-data formats.

Local implementation choices that do not alter package-wide rules belong in code, tests, and pull-request discussion rather than permanent architecture records.

## 15. Definition of architectural completion

The architecture is working when a new or modernized algorithm can be reviewed through a predictable set of questions:

1. Which numerical domain owns it?
2. What is its public mathematical contract?
3. Which inputs and intermediate values are validated?
4. How does it terminate, converge, or fail?
5. What is the natural R return value?
6. Which tests establish correctness, invariants, and failure behavior?
7. How is it documented and connected to the book?
8. Does a companion `cmna-el` implementation require a semantic parity review?

If those questions have clear answers, the package can grow without becoming either an unstructured textbook archive or an overengineered framework.
